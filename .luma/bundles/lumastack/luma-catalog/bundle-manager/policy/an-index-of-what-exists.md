# An index of what exists

**Load the index, never the content.** Something always present names what a
bundle holds and when each thing matters; the content itself loads when the work
turns out to need it.

**The rule, in one line: make existence cheap and content expensive.**

## The failure it prevents is silent, which is why it needs a rule

A consumer working to a budget leaves things unloaded. That is correct and
unavoidable. **The danger is that it cannot tell the difference between
*nothing applies here* and *I did not look*.**

Both look identical from the inside — no rule was consulted, no procedure was
found, and nothing reported an absence. An agent that has never heard of a
policy does not go looking for one; it proceeds, confidently, and the omission
surfaces later as a decision somebody made without the rule they were bound by.

**An index closes exactly that gap and nothing else.** It does not make content
cheaper to load. It makes *ignorance* impossible: a consumer holding the index
can always see what it is not loading, and pull any of it the moment the work
matches.

## Thirty documents is thirty lines

That is the whole economic argument. The expensive part of a document is its
content, not the fact that it exists — so the index is a rounding error against
a single always-loaded policy, and it covers everything.

**It is not a summary.** A line per document: what it is, and when it matters.
Anything longer is the content arriving through a side door, and an index that
grows into an abstract has stopped being cheap.

## The format already has all three parts

**Nothing here is new machinery.** It is three existing things nobody has put
together:

| | |
| --- | --- |
| **`description`** on every document | The format's core fields — *"one-sentence summary; used by indexes and search."* The per-document line, already required in practice |
| **`index.md`** | The format reserves it — *"derived navigation for a directory; a rebuildable cache, not a source of truth"* |
| **`matches: eager`** on that index | what makes it the thing that is always there |

**Derived is the property that keeps it honest.** An index generated by reading
each document's `title` and `description` cannot drift from what the directory
contains, because it is rebuilt rather than maintained. A hand-written index is
a second source of truth and will disagree with the first — which is worse than
no index, since it reports a complete-looking list that quietly omits whatever
was added last.

## Where this is already the answer

Three separate problems have landed on it independently, which is the argument
for naming it once:

- **`find-decision`**, in the `lumastack/luma-catalog/decision-records` bundle, is `optional` —
  and the three lines that say it exists live in `record-decision`, which is
  no trigger of its own. The trigger is always there; the procedure is not.
- **Mandates that apply only sometimes.** A line per mandate — what it is, who
  mandated it, when it applies — so nothing concludes *no mandate applies* out
  of ignorance.
- **Conditional loading generally.** The cheaper thing to try before teaching
  `matches` conditions richer than the triggers it already has.

**If you are reaching for a `when` condition, try an index first.** It solves
the same problem without anything having to evaluate prose, and it fails loudly
rather than quietly — a missing index entry is visible where an unmatched
condition is not.

## What it costs, stated plainly

**The index must be regenerated, or it under-reports silently** — the same
failure it was built to prevent, arriving from the other direction. Deriving it
is what makes that a build step rather than a discipline.

**And it only works while it stays short.** An index nobody reads because it is
two pages long is loaded before every session and buys nothing — which is the
exact cost `matches: eager` exists to make somebody choose deliberately.
