# ADR-0006: Every container carries an index

Every container has an index; a container is entered by reading its index.
A bundle ships its own `INDEX.md`; the project index is generated by
`apply`.

## Problem

An agent needs to find the right knowledge without reading everything, at
every level: which bundle bears on the work, which document inside it, and
what to read first. The prototype answered this by generating a
description of each bundle into every adopting project, and grew four
defects from that placement: staleness between
applies, orphan files needing sweep code, generated content where
hand-edits reach, and document descriptions drifting from their
frontmatter.

## Decision

**One rule at every level.** An index names each member, what it is for,
and what brings it into play. The project is a container of bundles; a
bundle is a container of documents; future containers join by getting an
index, not a new concept.

| container | its index | opened when |
| --- | --- | --- |
| the project | `.luma/bundles/INDEX.md`, generated by `apply` | every session — the harness always loads it |
| a bundle | `INDEX.md` at its root, shipped inside the bundle and frozen at its version | its line in the project index matches the work, or on request |
| future containers — a catalog, a sectioned document | acquired on joining | the same rule, one level out |

**A bundle's index travels inside the bundle.** `INDEX.md` at the bundle
root — generated when the bundle is edited or published, checked by
`audit-bundle`, frozen by the adoption checksum, never touched by `apply`.
One generator owns the rendering, in foreman, with a check mode.

**The project index is generated by `apply`** at `.luma/bundles/INDEX.md`
from the manifest's membership and the bundles' own metadata.

**Indexes are renderings, and the frontmatter they render is
authoritative.** Ground truth is the documents' frontmatter and the
bundle's metadata; a tool may read an index mechanically, and where the
two disagree the frontmatter wins and the disagreement is a reportable
defect of that copy. Markdown, because the index is written for models
and humans.

## Why

**An index that describes one version of one bundle cannot go stale in a
project** — it is exactly as current as the copy it arrived in, and every
defect of the per-project placement stops existing rather than needing
management.

**The `index.html` precedent carries the concept unexplained**: every
container has one, you enter through it, it links inward.

## Alternatives

**Per-project generation of bundle descriptions** — the prototype's
shape; rejected for the four placement defects above.

**Derived at read time, no file** — cannot go stale, but requires the
tool to exist to see anything, against the committed-clone invariant.

**A flat document-level index, no bundle indexes** — no missed-bundle
failure, but the floor grows with documents; rejected for MVP with the
trade recorded: a document is unreachable when its bundle's line fails to
match. The promotion valve is deferred until a real miss is observed.

## Re-open when

A measured miss shows a bundle's entry burying a document that mattered —
that forces document promotion into the project index, not a reversal of
this record. Full reasoning: [bundle design MVP](../../backlog/plans/bundle-design-mvp.md).
